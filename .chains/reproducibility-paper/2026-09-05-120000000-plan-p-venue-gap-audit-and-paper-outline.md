# Plan P: reproducibility paper, torchretrieve vs SilverTorch / LiNR

Source: `docs/plans/reproducibility-paper.md` Parts A-C (plan "P"), planning document 2026-09-05; research and gap audit only. Ordering: G2 = roadmap Phase B, G3 / G4 / G7 / G8 = D1, G5 / G6 = D2 / D3, G1 / G9 = F1 / F3, G10-G16 = Phase G. ## 0. Summary
1. "Industry papers with no public code" is half wrong: Meta released `meta-recsys/silvertorch` (Apache-2.0, created 2025-10-07, last push 2026-07-23, no tags, 29 stars on 2026-09-05) with `fused_kmean_ann` (int8 dp4a, optional 1-bit filter mask), `fused_kmean_ann_with_partial_masks` (Algorithm 1 phases 2+3) and `fresh_index_post_processing`; LiNR has no public code (arXiv 2407.13218). So: a reproducibility study for both plus a replicability check of SilverTorch's kernels on our public data (G2).
2. Venue: ECIR 2027 Reproducibility (abstract 12 Oct 2026, paper 19 Oct 2026, 12 LNCS pages, "a successful reproduction of the work is not a requirement"), with SIGIR 2027 Reproducibility (~Feb 2027 by the 2026 proxy, 9 ACM pages, double-anonymous) as the chained resubmission and RecSys 2027 as the recsys-only fallback. KDD has no reproducibility track and excludes "purely replicative work".
3. The thesis called QuantizedIVF new work; it must be SilverTorch's Algorithm 1 with a deviations list (done at F1).
4. Six things no reviewer lets pass: no QPS / P95 / P99; single seed, no CIs; no external baseline (every SilverTorch speedup is "vs Faiss"); scale <= 5.4M vs 10M-80M / 240M / 1B; official kernels not run; the goodreads d128 / d256 filter sweeps on a stale oracle.
5. Effort to ECIR grade ~4 weeks incl. ~10 GPU-days (P0); SIGIR grade adds the scale ladder and three baselines (~3 more weeks).

TheWebConf 2027: abstract 18 Oct, paper 25 Oct 2026, no repro track. Reasoning for ECIR: the only CfP that accepts a failed reproduction in writing; 12 LNCS pages fit two claims tables and a deviations table; its efficiency audience; timing chains to SIGIR then RecSys. Risk: six weeks and ~10 A100-days; else go straight to SIGIR. For SIGIR, submit via an anonymised mirror (the PyPI name identifies the author).

Lessons from well-regarded reproducibility papers: explicit reproducibility criteria per target and equally tuned baselines (Ferrari Dacrema et al. RecSys'19); under-tuned baselines invalidate speedups (Rendle et al. 2019); enumerate variants of "the same" method ("Which BM25 do you mean?" -> "which SilverTorch"); reimplement inside a maintained toolkit (Pyserini / DPR replication); report protocol sensitivity (Sun et al. RecSys'20); organise by RQ (DIME, SIGIR'25); reproduce, then generalise across backends and query distributions (ConstBERT / ColBERT-v2, SIGIR'26); repro papers extend rather than strictly replicate (Said & Bellogín 2026); CIs, full distributions, multiple-comparison-aware tests (Fuhr; Hoefler & Belli); the filtered-ANN protocol is QPS at recall in {0.90, 0.95, 0.99} on a selectivity axis 0.1 %-100 % plus build time and memory (Big-ANN'23, FANNBench SIGMOD'26).

## B. Gap analysis
Claims (SilverTorch, `articles/silvertorch.md`): S1 80M e2e 1210 QPS under 200 ms P99 (out of scope); S2 10M unsharded 3802 QPS (partially: needs QPS + P99 and a Faiss-GPU baseline); S3 QPS 3.1x from 80M to 10M (a size ladder); S4 TCO (out); S5 fused INT8 IVF 2.2-14.7x lower latency than Faiss-GPU IVFFlat fp32 at recall 0.35-0.92 on 20M x 128, batch 16, top-k 2048; 31.3-51x vs HNSW, 4.6-49.2x vs Faiss-CPU at top-k 4096 (needs external baselines); S6 INT8 cannot reach 0.95 recall / no loss at 64 probes and top-2048; S7 bloom 291-523x vs CPU inverted index, 12.6-42.7x vs GPU forward index; S8 FPR 6.98 % at 512 bits -> 0.067 % at 1024, memory 1.2 / 1.8 / 2.4 / 4.7 GB vs 19.8 GB inverted, heuristic bits = max_values x K x 3; S9 co-design scratch 35.6 -> 18.2 MB, 1.55 -> 0.72 ms, 1.79-2.15x; S10 probed fraction (81M, 9,000 clusters, 256 probes scores 2.8 %); S11 OverArch (out); S12 no top-k cap; S13 transposed bloom index; S14 fresh index (out); S15 scale-out (out); S16 global int8 scale.
Claims (LiNR, `articles/linr.md`): L1 high pass rate (15.5M jobs, ~11 % pass): PyTorch V1 bs1 4.8 ms avg / 4.9 p95, V2 14.6 / 47.8, V1 faster than V2 (our fused V2 inverts it; paper §6 predicts the flip); L2 low pass rate: V2 1.9 / 2.1 ms dominates; L3 V3 512-bit keeping 1 % ~10 % further gain; L4 1B x 64d -> 7.5 GB, top-50M 97.6 ms p95; L5 V1 / V2 up to 240M x 128 fp16 on one A100; L6 live update (out); L7 native masking 100x slower than the custom kernel; L8 pre-filtering fixes liquidity; L9 MoL (out); L10 un-fused ops (deviation); L11 avg + p95, recall label@2000 (deviation).
