# Plan X: the library / harness boundary

Source: `docs/plans/library-harness-boundary.md`, planned 2026-09-15 on `development` at `76f8985`. A contract implemented by L WP-2 and V WP-V1, pinned by two tests. Moved to the public wiki as `docs/system/library-harness-boundary.md` on 2026-09-26, with the status of each clause as of that date.

Rule: the library retrieves; the harness measures. Whatever decides which items come back (a kernel, a filter, a cascade, a quantizer, an index layout, a query-time knob like `n_probe` or `candidate_pool`) is library code; whatever decides what to run, on what data, how to time it and what to write down is harness code. Tie-break: would a `torchretrieve` user who never saw this repo want it? The V3 cascade yes; the fingerprinted oracle blob no. At the time the rule was broken in one file: the harness `algos.py` owned V1-V4, `set_query_params` and `capturable`.

What the harness may import (as written): from `retrieve` the two backend literals, the two ABCs, `SilverTorch`, `SilverTorchBuilder`, `OfficialConfig`, `LiNRV1`-`LiNRV4`, `LiNRBuilder`, `BloomFilter`, `ExactAttributeFilter`; `retrieve.functional`; `retrieve.interfaces.DISPATCH`. Not allowed: `retrieve.ops` (kernel-only numbers are `tune-kernels` or `--profile`), `retrieve.indexing` (ablations are module constructor args: `kmeans_init`, `m_bits`, `k_hash`, `n_lists`), `retrieve.modules.knn` / `bit_knn` (new compositions go into the library first), `retrieve.modules.official` (reached via `SilverTorch(backend="official", official=OfficialConfig(...))`; the S9 ablation is `bloom_path="full"`).

Ownership table: library owns V1-V4 compositions, `set_query_params`, `capturable`, SilverTorch incl. the official adapter, filters and kernels, k-means / quantizers / bloom hashing / IVF layouts (only via constructor args), top-k / compaction glue, autotuning, `FullScanKNN` as a module (not the oracle). Harness owns the filtered oracle (`attrs_digest`, blob v4, `target_in_filter`, `pass_rate`), metrics (training keeps a frozen copy), latency / memory / provenance / clocks / graph capture / sync detection (`graph_callable` reads `module.capturable`), the algorithm table and `PATHS` (derived from `DISPATCH` by a test), record identity / storage / resume / `flat.csv`, query encoders, datasets and the on-disk layout, tables and figures, and any `torch.compile` / CUDA-graph capture (the library never compiles internally; official refuses).

Library promises (all delivered by L2 or earlier): one `forward(query, query_clause_attrs=None) -> (ids, scores)` with `-1` / `-inf` sentinels on every algo-level module; `module.k` settable after registration; `set_query_params` re-validating without rebuild; `SilverTorch.build_timings`; all index state in `buffers()` with the filter a submodule; `capturable` on every algo-level module and no host sync on the triton / torch forward; the salt a buffer (B5); `ValueError` for unsupported backends (B4); `DISPATCH`; builder round trip + load hook; `OfficialConfig.cache_plans` at construction; bit-exactness between backends is the library's parity suite, never the harness's job.

Amendment the same day, from C4: §4's last clause read by H WP-4 as `jaccard_vs_first@100 == 1.0` for "exact algos" is wrong: exact describes exact filtering (no approximation in candidate selection), not bit-identical arithmetic between two implementations of an fp16 dot. Evidence then: `linr_v2` 0.998743 torch vs triton, `score_max_abs_diff` 9.77e-3 (reproduced independently by the golden at 4.2e-4 recall); `linr_v1` / `linr_v4` exactly 0.0; SilverTorch exactly 1.0 / 0.0. L4 found identical candidate sets and fp16 accumulation in the Triton kernel; L5 moved it to fp32 (jaccard 0.999751, the residual being torch's own fp16 output ties).

Gates: harness side `evaluation/tests/test_dependency_direction.py` (every import resolved with `ast` against the allow-list); library side `retrieve/tests/correctness/test_boundary.py` (k mutation without re-registration, `buffers()` covers every tensor, forward clean under `set_sync_debug_mode("error")`, builder round trip, `capturable` on the class, `DISPATCH` complete); `tests/bench/test_paths.py` asserts `PATHS == derive(DISPATCH)` (replacing a markdown-parsing test of architecture.md).

Naming map (paper / library / harness): LiNR V1 = `LiNRV1` over `PostfilterKNN` = `linr_v1_filter_mask` (cuBLAS either way); V2 = `LiNRV2` over `PrefilterKNN` = `linr_v2` (filter required, no `none` cell); V3 = `LiNRV3` (`OneBitKNN` -> `PrefilterKNN`) = `linr_v3` (`candidate_pool` a query param); V4 = `LiNRV4` over `PostfilterKNNInt8` = `linr_v4` (ours, not the paper's); SilverTorch Algorithm 1 (was "QuantizedIVF") = `SilverTorch` = `silvertorch` (`n_probe` a query param); Meta's official ops = `SilverTorch(backend="official")` = `silvertorch` + `backend: official`; exact / bloom filter = `ExactAttributeFilter` / `BloomFilter` = `filter_kind: clause` / `bloom`.
