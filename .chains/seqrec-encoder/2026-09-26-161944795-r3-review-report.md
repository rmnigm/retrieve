# R3 review report: dev/hstu-logq

Branch `dev/hstu-logq`, fixes committed as `44d402a` on top of `9d40f00`. Not pushed or merged.

## Verdict: BLOCKING (F1, F2 need a user decision; the code otherwise checks out)

## Fixes applied
- `losses.py` `sampled_softmax_loss`: removed the `log_q=None` default. Its only callers (step_loss, the test) always pass it.
- `train.py` `step_loss`: removed the `p_train=None` default. Its one caller (`train()`) always passes it.
- `docs/system/datasets.md` § The losses: "With M = 0 ... the correction is a constant that changes nothing" was wrong. The constant `+log N` goes onto the candidates only, not onto the uncorrected positive, so it changes the loss. The doc now says that.

## Checked and correct
- `log_q=None` is bit-identical to the pre-branch loss. `torch.equal` holds on 60 random CPU cases (normalize on and off, T ∈ {0.05, 0.07, 1.0}) against `dev/hstu:losses.py`. Moving the `/T` changes nothing because the division is elementwise, and −inf/T is still −inf.
- M = `perm.shape[0]` = min(inbatch_negatives, P) and K = `num_negatives` are the counts actually drawn. `p_train[candidates]` indexes an [N+1] vector with ids 1..N.
- `target_frequencies`: `items` is `[U, L+1]` (dataset.py:27), so columns 1 onward are exactly the targets `step_loss` trains on. Subtracting column 0 and zeroing index 0 give the hand counts on a toy.
- dtype: autocast leaves float64 alone. The `.log()` result stays float64 under a bf16 autocast (checked on CPU), then `.float()`. q_j ≥ K/(N(M+K)) > 0, so `log_q` is always finite.
- Masking: `log_q` is subtracted first, then accidental hits are set to −inf, so they stay −inf. The positive is never corrected.
- `logq` is recorded in `config.json` and wandb through `asdict`, and parsed by the generic `train run` overrides.

## Open findings
- **F1: normalization of q (train.py:104, datasets.md:1141). Changes behaviour, so not fixed.**
  - Mechanism: the importance-sampling estimate of the negative mass Σ_i e^{s_i} is Σ_{draws} e^{s_j}/E[count_j], with E[count_j] = M·p_train(j) + K/N. That means subtracting log(M·p + K/N).
  - The code divides that by (M+K) and uses the per-slot probability. Every candidate therefore gets an extra `+log(M+K)`. Because the positive is not corrected, this shift does not cancel: it inflates the negative mass by a factor of M+K.
  - It is the same convention as Yi et al.'s in-batch q (the per-batch probability, ≈ B·p).
  - I did not confirm which convention arXiv 2507.09331 states for the uncorrected-positive variant, so this needs a decision.
  - Fix if chosen: drop `/ (m + k)` and update the q_j formula in datasets.md.
  - The oracle test takes an explicit `log_q`, so it pins neither convention.
- **F2: standing decision contradicted (docs/decisions.md:133, :143).**
  - decisions.md says the loss uses "no logQ (HSTU's own recipe)" and lists "Out of scope for this line: logQ".
  - The branch adds logQ as an opt-in flag (default off, so the recipe is unchanged) but leaves decisions.md alone. Under the contradiction policy, the user has to amend the decision (for example "logQ available as an opt-in experiment"), or the branch goes against a standing decision. decisions.md is outside this diff, so I did not touch it.
- **F3 (minor, known from W3): no gate covers `target_frequencies` or the q_j formula in `step_loss`.** Only hand checks exist, W3's and mine. The brief allows no new test unless it pins a fixed bug. If F1 changes the formula, a small test of `log_q` for a fixed M, K, N and p would pin whichever convention is chosen.
