# W9 report: `resume_every` (resume-checkpoint cadence)

Branch `dev/hstu-ckpt`, commit `169c3c9`. Not pushed or merged. CPU only, no GPU used.

## Mechanism (before)
- `_resume.pt` (`train.py` ~166 path, ~275 write): written **every epoch**. It holds the model state dict
  plus AdamW `exp_avg` and `exp_avg_sq` (plus scheduler, counters and RNG, which are negligible).
  That is 3 × the model. At KuaiRand d64 (two 32,038,726 × 64 fp32 tables = 16.4 GB model) it is
  **49.2 GB**, taking ~45 s per epoch.
- Best snapshot `sasrec-ep{N}-….pt` (~271): model only, **16.4 GB**, ~15 s, written on each new best.
- `best_model.pt` (~303): once per run. The best snapshot is reloaded and then re-saved (16.4 GB).

## Change
- `TrainConfig.resume_every: int = 1`. With the default, existing recipes behave as before.
- `resume_due(epoch, config, stopping)` returns true every `resume_every` epochs, on the last epoch,
  and on an early-stop exit. `best_model.pt` is unchanged.
- **A correctness fix the option needed (in scope because it guards the option).** The old code deleted
  the previous best snapshot as soon as a new best appeared. With N > 1, a crash between `_resume.pt`
  writes left `_resume.pt` naming a deleted file, and the resumed run then died at the final
  `torch.load(best_path)`.
  - Now a superseded best is deleted at once, **unless** the current `_resume.pt` names it. That one is
    deleted after the next `_resume.pt` write.
  - On `--resume`, `sasrec-ep*.pt` files newer than `_resume.pt` are deleted (they belong to epochs
    being retrained).
  - Disk peak rises by at most one best snapshot (+16.4 GB at k64).
  - The same crash window already existed at N = 1, between the unlink and the resume write, and is now closed.
- Step 3 (a cheap win): **none found in the per-epoch path**. It has no redundant `.cpu()` and no double
  serialization within `_resume.pt`.
  - On an epoch that is both a new best and a resume write, the model is serialized twice (snapshot +
    inside `_resume.pt`). Avoiding that would change what `_resume.pt` contains, which is out of scope.
  - The end-of-run `best_model.pt` re-save (16.4 GB, ~15 s, once per run) could be a hardlink of
    the snapshot. It happens once per run, not per epoch, so I left it out.
- Docs: `docs/system/datasets.md` § Training documents the option, the byte and time cost, the
  trade-off (a crash loses up to `resume_every − 1` finished epochs, which `--resume` retrains),
  the snapshot lifetime and the disk peak. The tree comment is updated too.

## Recommendation for KuaiRand d128
**`resume_every=5`.** With one 32 M × 128 table, `_resume.pt` is again ~49.2 GB, ~45 s per write.
- At every 5th epoch the cost averages ~9 s per epoch (≈4 %, down from ≈20 %).
- A crash loses at most 4 epochs (~15–20 min at ~210–250 s per epoch).
- The best-snapshot writes (~15 s per new best) are unchanged.
- It is not yet measured on the GPU: the numbers are arithmetic from the k64 probe.

`docs/validation.md` is not touched: no gate changed.
