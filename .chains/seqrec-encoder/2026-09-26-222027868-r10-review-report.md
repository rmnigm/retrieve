## Fixes applied
- `train.py:188`: the resumed `best_path` is now `ckpt_dir / <stored file name>`, so the
  pruning glob compares like with like.
  - Mechanism before: the glob yields `ckpt_dir/…` in the current spelling, while `state["best_path"]`
    kept the old run's spelling. If the two differ (relative vs absolute `checkpoint_dir`, or a moved
    directory), `snapshot != best_path` is true for the real resumable best, so it was **deleted**.
  - The resumed run then crashed at the `resumable_best.unlink()` after the next `_resume.pt` write
    (`FileNotFoundError`). Without a new best, it would have crashed at the final `torch.load(best_path)`.
  - Reproduced on CPU: crash in epoch 4 with N=3, then a resume with an absolute
    `checkpoint_dir` → `FileNotFoundError: 'ck/sasrec-ep2-…'`. After the fix it resumes at epoch 3
    and finishes.
- `train.py:196-200`: the prune now runs on every `--resume`, not only when `_resume.pt` exists.
  - Mechanism before: with N>1, a crash before the first `_resume.pt` write (epochs 0..N-2) left the
    current best snapshot on disk.
  - `--resume` then started fresh and never saw that snapshot, so it leaked permanently (16.4 GB at k64).
  - Reproduced: after the rerun, `ep0` and `ep6` were both left on disk; after the fix, only `ep6`.
- `docs/system/datasets.md` § Training: the snapshot sentence now says the best is looked up by file name in
  `checkpoint_dir`, and that `--resume` deletes every other snapshot, including when no `_resume.pt` exists yet.
- deslop: nothing else to remove. The diff is lean, and its two comments are short why-notes.
- No test was added for the fix. Pinning it needs a `train()` run on CPU with parquet fixtures, which is
  scaffolding beyond D6. The smoke script used (not committed) is in the r10 scratchpad.

## Crash walk (after the fix), N=1 and N=5
Invariant: the snapshot that `_resume.pt` names (`resumable_best`) is never unlinked before a newer
`_resume.pt` has been written. On disk there are at most two snapshots: `resumable_best` and `best_path`.
- **Crash between the unlink of the superseded best and the save of the new best**: `_resume.pt` names
  `resumable_best`, which is still on disk. OK.
- **Crash during the new snapshot's `torch.save`**: the partial file has a new name; `--resume` deletes it. OK.
- **Crash after the snapshot, before `_resume.pt`**, and at N=5 **between resume writes**: the newer
  snapshots are deleted on resume. Epochs are retrained from `next_epoch`. A resume never loads a
  snapshot newer than its state. OK.
- **Crash between the `_resume.pt` write and `resumable_best.unlink()`**: the old snapshot would leak,
  but it is removed by the next resume's prune. There is no permanent leak.
- **Crash before any `_resume.pt`** (N=5, epochs 0-3): the fix above covers it.
- **Final `best_model.pt`**: `best_path` is never unlinked while it is current. `resume_due` is true on
  the last epoch and on an early stop, so a finished run leaves exactly one snapshot, and `_resume.pt` names it.
- **Boundaries**: epoch 0 writes only if N=1 or `num_epochs=1`. The last epoch and an early stop
  always write. `stopping` requires an eval epoch, as before.
- **Test mutation strength** (`test_encoder.py:122-130`): the test catches the three mutations W9 lists.
  The inline `stopping` expression in `train()` is not covered, which is acceptable for a pure helper.

## Open findings
- **F1 (pre-existing, not introduced; highest crash exposure)**: `train.py:288`. `_resume.pt` is written
  in place with `torch.save`.
  - Mechanism: the file is opened `wb`, which truncates it, and the write then takes about 45 s at 49.2 GB.
    A crash in that window destroys the only resume state. `--resume` then fails in `torch.load`, and the
    run restarts from scratch (the prune now at least frees the snapshots).
  - The fix is to write to a temporary file and `os.replace` it. That raises the peak to 2× `_resume.pt`
    (~98 GB at k64) on the quota volume, which is a disk decision for the user or orchestrator.
    N=5 cuts the exposure fivefold but does not remove it.
- **F2 (minor, D1 boundary)**: `config.py:36`. `resume_every=0` is not rejected at construction.
  - It fails with `ZeroDivisionError` at the end of epoch 0, after a full epoch of GPU time.
  - A one-line check in `__post_init__` would fix it. I left it out: `eval_every` has the same gap, and
    fixing only one of the two would be inconsistent.
- **F3 (pre-existing, minor)**: a fresh run without `--resume` in a directory that already has an old
  `_resume.pt` leaves that file in place until its first resume write, which is up to N epochs.
  - A crash in that window, followed by `--resume`, silently continues the **old** run.
  - At N=1 the window was one epoch.
- Docs: `datasets.md`, `storage.md` and `checkpoints.md` agree with the code. `validation.md` is untouched:
  no gate changed.
- The 49.2 GB / ~45 s / "a fifth of a ~210 s epoch" figures in `datasets.md` are cost notes from the k64 probe
  in a system page. They are not presented as citable results. The d128 `resume_every=5` estimate stays in the W9
  report only.
