# Blocked: KuaiRand d128 OOMs even with reuse_item_embeddings=true

Probe (d128, one table, train_on_val, 200 batches) 22:35:50-22:37:22 UTC, H100 79.18 GiB:
`torch.OutOfMemoryError` in `loss.backward()` (train.py:217) at the **second** step: "Tried to allocate
15.28 GiB ... 14.71 GiB free ... 62.98 GiB allocated by PyTorch".

Mechanism (arithmetic that matches the reported numbers): one 32.04 M x 128 fp32 table = 15.28 GiB.
Weight + two AdamW moments = 45.8 GiB, resident after step 0. The shared table then takes **two dense
gradients** in backward (input lookup and output scoring), held at full size before they are summed
(+30.6 GiB), plus ~1.9 GiB activations: ~78 GiB. The failure came at 62.98 GiB allocated, when the second
15.28 GiB gradient was requested. The instruction's estimate (~66 GB for one table) did not count the
second gradient.

Per the go note: stopped, no memory engineering tried. k128-refit not launched; the queue runner exited;
no probe checkpoints are left. Options for the user: skip KuaiRand d128 (k64-refit stands: 0.0276 /
0.0063); or change the code so the table's gradient or optimizer state is smaller (sparse/row-wise
Adagrad, bf16 table or moments, a catalog cut to items seen in train + val). Each is a code change
through review.
