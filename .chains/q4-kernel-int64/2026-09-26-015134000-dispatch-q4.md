# Q4: int64 kernel offsets and the library findings (GPU, risky)

## 1. Request
Roadmap Q4. Fix a latent int32 overflow in every Triton kernel and a set of smaller library findings. Marked **risky** by the user: it changes `code_version` (tree hash of `retrieve/src/retrieve`), so D1's records stop measuring the shipped code, and it touches every kernel's addressing. Kept in the plan; blocks F4 (the release must ship it). Ideas only; cite only this repository.

## 2. The overflow (verified by reading; not reproduced)
Triton `program_id` is int32 and integer strides arrive as int32 when below 2³¹, so products wrap:
- **Output axis**: `bid * stride_ob` style offsets (`ops/triton/clause_mask.py` store, `oporp_1bit_match_topk.py`, `fused_masked_knn_topk.py`, the other `bid`-indexed kernels) wrap at B·N ≥ 2³¹, e.g. B ≥ 144 at N = 15M.
- **Item axis, any B**: `n_off[:, None] * stride_s_n` in `bloom_match.py` / `bloom_compact.py` wraps at N·W ≥ 2³¹ (N ≥ 134M at W=16); `common.py` `ids * stride_in` via `clause_mask`/`clause_compact` at N ≥ 107M (C=5, A_max=4); `oporp` item stride at N ≥ 1.07B.
Gathers through int64 ids are already safe. No produced number is affected (eval batches ≤ 16, N ≤ 15M); the synthetic scale ladder (G-b, 240M-1B) and library users at large B are.

**Fix idea**: widen once on the scalar base pointer — `row0 = tile_id.to(tl.int64) * BLOCK_N`, `ptr += bid.to(tl.int64) * stride_b + row0 * stride_n` — and keep lane offsets (`tl.arange`) int32 relative to that base, so the vector math costs nothing extra. Apply uniformly through one small helper or one idiom used identically in every kernel (not per-file improvisation). Document the addressing rule and bounds in `docs/system/kernels.md`.

## 3. Other findings to fix
- **fp32 scalar pin**: float scalar kernel arguments (`global_scale`, `q_scale` in `codesigned_probe_score*.py`) may be specialised fp32 by eager Triton but fp64 when launched from Inductor; cast to `tl.float32` in-kernel. Unverified whether it bites on torch 2.10; the fix is a no-op in eager.
- **Compaction −1 tail**: `_host.py` does `torch.full((b, n), -1)` before every compaction (~1.9 GB writes at B=16, N=15M, unmeasured). Profile it with `torch.profiler`; move the fill into the scatter kernel (it writes −1 past its row's count) and allocate with `torch.empty`. Dropping the −1-tail contract entirely is a user decision (roadmap "Needs the user"), not this step.
- **Boundary validation instead of silent copies/crashes**: reject non-contiguous item-side tables (today `.contiguous()` silently copies N·W·8 bytes per call); keep copies for small query tensors. Reject `D` that is not a power of two in `fused_masked_knn_topk` prep with a `ValueError` (today it would fail inside the Triton compiler — verify). `pytest.raises(match=)` gates for both.
- **Tuner discipline** (`ops/tune.py`): the current `DEFAULT_CONFIG` stays unless a candidate beats it by more than a stated noise band; reject a candidate that slows the worst regime beyond a cap; `--json-out` records `sm_mhz`, commit, torch/triton versions. A separate B=1 config only if the per-regime data shows ≥10 % gap.
- **Dependency floors = validated versions**: `retrieve/pyproject.toml` says `torch>=2.4` but `torch.library.triton_op`/`wrap_triton` need a newer torch (check which); set floors to what was validated and add a "validated on" line (A100 sm_80, torch/triton versions) to `retrieve/docs/getting-started.md` and `retrieve/README.md`.
- **Lint and comments on `retrieve/`**: the same ruff widening Q2 applied to `evaluation/` (bugbear incl. `zip(strict=True)` — ~10 hits, e.g. `functional.py`), dated/history comments moved out (`ops/triton/clause_mask.py:21`, `ops/official/__init__.py:72`), stale comment in `fused_masked_knn_topk.py` (~191, "compact kernels use torch.empty"). Overlaps the retrieve-cleanup chain Batch 2 — do once, whichever runs first.
