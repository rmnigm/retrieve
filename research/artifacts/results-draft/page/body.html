Where SilverTorch reaches the recall you ask for, it beats LiNR in all but one cell

Two families of filtered GPU retrieval on one A100: SilverTorch (Meta's official code, adapted by us) probes a few clusters of an int8 index and filters them with its bloom filter, false positives allowed; LiNR (V1 mask-then-score, V2 gather-then-score, V3 a 1-bit prefilter, our implementation from the paper) filters exactly. Every SilverTorch point was timed in the same process as LiNR, on five datasets from 0.8 M to 30 M items.

ⓘPreliminary, not citable. These are the final rerun's numbers at seed 0, rebuilt as its runs land; the rerun's gate is not passed yet. Recall here means fidelity to exact search: the share of the exact filtered top-k (highest inner products over the whole catalogue, same filter) that a method returns, so a bloom false positive in the top-k counts as a miss. It is not the papers' end-task recall, but . Cells unstable in every run are marked †.

3 · SilverTorch's own settings

Recall follows the share of clusters probed; more clusters cost build time, not memory

How to read it: left, recall@100 against the share of clusters probed, one line per number of clusters (bloom filter, no recheck). Right, time per batch against recall at the settings that were timed, labelled by probes; the dashed line is the best exact LiNR in the same run. At the same share probed, 4,096 and 65,536 clusters give about the same recall, but building 65,536 takes 17× longer (LAION 30M: 105 s against 1,738 s) for an index only 0.5 % larger. More probes cost time: on arXiv at a batch of 16, going from 24 to 512 probes takes 0.19 ms to 0.61–1.01 ms, still under exact LiNR's 1.8–2.1 ms.

6 · Why a probabilistic filter

The bloom filter is faster than a well-engineered exact filter in the same search

How to read it: SilverTorch (Meta's code, adapted) with its bloom filter against the same search with an exact clause filter fused in its place, at the same clusters and probes, from two separate runs on the same GPU (not interleaved; the exact filter's run is a later build whose bloom path is byte-identical), with pairs unstable on either side dropped. A number below 1 is the bloom's time as a share of the exact filter's. The bloom's price is its false positives: a passing-looking item that fails the filter and takes a top-k slot. That supports SilverTorch's case for a probabilistic filter; the paper's other half is how few false positives it lets through.

8 · Inside LiNR

LiNR's V2 beats V1 only for one query at a time

How to read it: below the line V2 (gather the passing items, then score) is faster than V1 (score everything, mask). At bs 1 V2 wins below a pass rate of about 0.8–0.94, by more as N grows. At bs 16 the crossover drops to 0.01–0.05; at bs 64 and 256, V1 wins on every filter.

9 · Co-design

Meta's "probe, then filter" pays off only at 10–30 M items

How to read it: above 1, filtering inside the probed clusters (the paper's co-design) beats building the filter over the whole index first. Measured on Meta's code as published: the paper's 1.79–2.15× shows up at 30 M; below 10 M the full-index path is faster. The adapted code has no full-index path to compare: it filters only the probed clusters by design.
